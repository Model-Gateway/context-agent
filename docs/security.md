# Security model

**Permission profiles.** Three tiers. `approval_required` (default) prompts for edits and for any command that is not read-only. `workspace_autonomous` allows edits and build/test commands inside the workspace without prompts, and prompts for network, destructive and unrecognised commands. `bypass_permissions` never prompts: edits, deletes, network, destructive and unrecognised commands all run immediately. Denied command prefixes, credential files and paths outside the workspace roots are still refused under every profile. In the TUI bypass is chosen only by name (`/approval bypass`), never by Shift-Tab cycling, and like every profile it cannot be set from a repository's `.context-agent.toml`. The former `read_only` and `sandbox_autonomous` profiles are gone: a configuration or `permissions/set` naming them is rejected. Read-only work is now a property of a tool set, not a profile: `explore` sub-agents (below) get inspection tools only.

**Sub-agents (Ultra effort).** With `model.reasoning_effort = "ultra"` the lead agent gets a `spawn_agents` tool. Each sub-agent is a runtime of its own (`agent.agent_max_steps` steps when set, at most `agent.max_parallel_agents` at a time, `agent.max_agents_per_call` per call) under the **same** permission profile and the same remembered approvals, so an `implement` agent's edits and commands prompt exactly as the lead's would (approval ids carry an `@<agent id>` suffix so two agents' calls never collide). `explore` agents have no editing or shell tools at all. Agents never spawn agents. Their files and token usage are folded into the lead task; their reports are data to the lead, rendered with the same untrusted-content delimiters as tool output.

**Command wrapper (developer mode).** `[permissions.sandbox]` (`kind = "wrapper"`, `wrapper = [...]`) prefixes every shell command with a wrapper such as a container runner. It is a facility for tests and developers, not a permission tier: the policy engine never allows anything because a wrapper is configured, and `ctx doctor` reports it when set.

**Web search and fetch.** `web_search` sends its query to a search provider: the signed-in ModelGateway account by default, otherwise a configured provider or DuckDuckGo (`[web_search]` in docs/configuration.md). The query passes through credential redaction before it is shown for approval or sent. `web_fetch` downloads one http(s) URL; it refuses URLs with embedded userinfo or anything the credential redactor would blank out, so a key cannot be smuggled out in a query string. Both prompt under `approval_required` (unless `allow_network_commands` is set) and run without a prompt under `workspace_autonomous` and `bypass_permissions` — except that fetching a loopback, private, link-local or unique-local address, or a `localhost`/`.local`/`.internal`/single-label name, prompts under every profile but bypass, and a public page that redirects into such an address is refused. Hosts are classified by name, not by DNS lookup, so a public name that resolves to a private address is not caught. Set `enabled = false` in either table to remove a tool. Results and pages are untrusted content like any other tool output. `explore` sub-agents have both tools.

**Paths.** Built-in file tools resolve paths against the workspace roots, follow symlinks before checking containment, and refuse credential patterns (`.env`, `*.pem`, `id_rsa`, ...). Those files are also excluded from the index.

**Commands.** A conservative classifier splits pipelines and labels each segment read-only, build/test, write, network, destructive or unknown; the highest class wins. It looks through wrappers (`env`, `nohup`, `timeout`, `xargs`, `find -exec`/`-delete`), treats command substitution (`$(…)`, backticks, `<(…)`) as at least unknown, and skips git's global options (`git -c … push`). `allowed_commands` prefixes apply to whole commands only: `npm test && npm publish` is not covered by `npm test`. A model-supplied `run_validation` command override is evaluated exactly like `execute_command`; only commands from configuration or build-file detection count as validation. Path validation does not sandbox shell commands; the profile and approvals compensate.

**Repository configuration.** A repository's `.context-agent.toml` may tune `[index]`, `[context]`, `[validation]`, `[agent]` and `[embeddings]` only. `[model]`, `[permissions]`, `[telemetry]`, `[web_search]`, `[web_fetch]` and `[pricing]` are ignored from that file (and reported by `ctx doctor`), so cloning an untrusted repository cannot redirect the API key, change the permission profile or disable approvals.

**Session approvals.** "Approve for this session" remembers the exact action (tool, summary and the full command text or patch); a different edit to the same file prompts again.

**Prompt injection.** Repository content, tool output, memories and checkpoints are rendered as data with explicit delimiters and a preamble; the system policy instructs the model to treat anything inside as untrusted. Only the policy, repository summary and runtime notes are trusted instructions.

**Credentials.** API keys are read from environment variables, registered with the redactor (together with any `*_KEY`, `*_TOKEN`, `*_SECRET` variables), and removed from events, logs and diagnostics. Tool output shown to the model receives credential-pattern redaction only, so code remains readable.

**Concurrency.** Patches carry the file hash they were based on and are rejected when the file changed; retrieval re-verifies hashes before supplying snippets; the indexer treats any changed file as potentially modified by another agent or a human.
